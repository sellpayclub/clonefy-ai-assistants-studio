# Recuperação de login e agentes — 21/09/2026

## Diagnóstico e intervenção

O banco respondia ao SQL administrativo, mas Auth e REST estavam UNHEALTHY. Chamadas públicas excediam 25 segundos, e os logs de Auth registravam HTTP 500/504 durante login/refresh. O status geral ACTIVE_HEALTHY não refletia a saúde dessas APIs.

Foram confirmados 132 agentes, 67 ativos e zero vínculos órfãos. RLS está habilitada em assistants, com leitura restrita a auth.uid() = user_id. Agentes inativos não foram reativados: a listagem mantém o filtro existente is_active=true.

A reinicialização do projeto Supabase recuperou Auth, REST e banco. Não houve alteração de esquema, políticas, senhas de clientes, planos ou configurações de cobrança. A causa imediata foi indisponibilidade dos serviços; a causa de infraestrutura que levou à degradação não foi conclusivamente identificada. Houve consultas internas lentas e uso de swap, portanto reiniciar não garante que o incidente não se repita.

## Correções no aplicativo

- Leitura dos agentes diretamente no Supabase com RLS e filtro de proprietário, removendo a dependência de Edge Function/OpenAI para exibir dados já salvos.
- Uma fonte de autenticação nas telas de login e agentes; remoção da assinatura duplicada que não era encerrada ao desmontar a tela.
- Proteção contra restauração tardia de sessão sobrescrever um login recente.
- Cache de agentes por usuário, compartilhado entre agentes e calendário, novas tentativas limitadas e recuperação ao reconectar.
- Preservação da última lista válida durante falha de atualização e indicação visual do erro, sem tratar indisponibilidade como lista vazia.
- Correção da função de consulta congelada que podia continuar usando filtros antigos.
- Logout local e limpeza de caches; falha no servidor não impede remover a sessão local desse projeto.
- Prazo de 20 segundos para requisições REST/Auth, preservando cancelamento e sem limitar uploads/funções de IA ao mesmo prazo.
- Erros de infraestrutura diferenciados de credenciais inválidas ou email não autorizado.

As correções são de frontend. Não exigem migração SQL ou publicação de Edge Functions. Sincronizar o GitHub no Lovable e publicar o frontend incorpora as mudanças.

## Validação

- 11 testes automatizados: isolamento entre usuários, falha de primeira carga, preservação e recuperação da lista, mudança de filtros, corrida na restauração de sessão, limpeza no logout, timeout e cancelamento.
- npm test: aprovado.
- npx tsc --noEmit -p tsconfig.app.json: aprovado.
- npm run build: aprovado.
- Navegador local: tela de login renderiza; rota protegida redireciona visitante sem sessão para login.
- Supabase real, usando a chave pública do aplicativo: login por senha HTTP 200 (~290 ms), refresh HTTP 200 (~73 ms), criação temporária via openai-assistants HTTP 200 (~455 ms), leitura REST do agente HTTP 200 (~48 ms) e listagem pela função HTTP 200 (~224 ms).
- Conta temporária sem agentes não conseguiu consultar agentes de outros clientes. Conta e agente de verificação removidos após o teste.

## Pendências e limites da auditoria

- Lint geral permanece com 452 erros e 41 avisos; a versão original tinha 457 erros e 43 avisos. Não foram adicionados erros de lint. A maior parte é dívida de tipagem/hooks preexistente, e não falha de compilação.
- npm audit --omit=dev: duas ocorrências moderadas em react-router/react-router-dom, sem ocorrências altas ou críticas. O npm sugere atualização principal do roteador; essa migração requer validação própria e não foi aplicada junto da recuperação.
- A amostra de métricas após reiniciar indicava cerca de 423 MiB de RAM total, 79 MiB disponíveis e 322 MiB de swap em uso. Esses números não provam a causa do incidente; capacidade e carga das rotinas periódicas devem ser avaliadas se os timeouts voltarem.
- Não foi feita validação ponta a ponta de mensagens reais de WhatsApp/Telegram/Meta, pagamentos, agendamentos externos ou geração de respostas de todos os agentes. A recuperação validada cobre login, refresh, criação e listagem de agentes; não certifica todas as integrações do produto.
- O frontend publicado pelo Lovable ainda depende da sincronização/publicação pelo proprietário.

Para repetir os testes locais: npm ci && npm test && npx tsc --noEmit -p tsconfig.app.json && npm run build.
